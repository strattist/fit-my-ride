How Fit my Ride works, from a rider's tap to a bike's data

No technical background needed. This explains what the system does, why it is built this way, and which decisions are still ours to make.

The two stories

The whole product is two stories. One is a rider checking a bike. The other is one of us adding a brand's bikes. Everything else supports these.

Story 1. A rider checks a bike

  1. You open the app (on a phone it can be installed like an app) and enter height, cycling inseam and riding style.
  2. The app looks up the saved bikes. Each bike comes in several frame sizes. For each bike the app picks the size that suits you best, so you see one row per bike.
  3. Each of the five measurements is compared to your ideal range. The cell is coloured on a scale: too short, ideal, too long.
  4. You sort by any column, or by how many measurements are in range.

Nothing about you is saved on the server. Your numbers travel in the page address, so you can bookmark or share a link. There are no accounts and no profiles.

Grey cells. A grey cell means we have no way to judge that measurement for you, not that it is bad. At the moment every cell is grey, because the judging rules haven't been written.

Story 2. Adding a brand's bikes

  1. Start with the brand's PDF of frame measurements.
  2. A small module for that brand reads it. Each brand lays out its PDF differently and names things differently ("Stack", "Frame height"...). Each module knows its own brand.
  3. An AI model helps read the tables. Its answer is checked against a fixed format, and anything unreadable is flagged.
  4. Names and units are translated into our standard ones. Our standard is Van Rysel's naming. Lengths are in centimetres and angles in degrees.
  5. If two sources disagree, a fixed rule decides: an official brand source beats an unofficial one, and the most recent official one wins.
  6. A person reviews everything. A summary lists every value, its source and any conflict. You approve or abort. Nothing is saved before you approve.
  7. Approved data is saved as plain files in the project. The app's database is rebuilt from those files.

Rule: a bike that lacks any of its five core measurements is not saved. The review lists it, and the rest of the batch can still go through.

Where the AI is, and isn't

Used

Only to read a brand's PDF while one of us is adding or refreshing that brand, on that person's own computer.

Never used

When a rider uses the app, when judging fit, when settling conflicts, or in the review. Those are fixed rules or a human.

Consequences: no AI cost when people use the app, and the server never holds an AI key.

The rules that keep two builders and several AI coding agents in step

  • The meaning of things is written once. What "in range" means, what a unit is and how a conflict is settled each live in one place, used by both the app and the data side.
  • The app only reads data. Only the approved-file path can change what bikes exist.
  • Each brand is its own module with the same shape, so a new brand cannot break the others.
  • Same checks everywhere. A formatter and the tests run on each of our computers and on GitHub, in identical form.
  • Access is handled in front of the app. Your existing sign-in (Authentik) and HTTPS protect it; the app itself has no accounts.

Where it runs

On the home server, in one container. Bike data goes in as files from the project and the app opens them read-only. If the server is lost, rebuilding means pulling the project and starting the container. Nothing lives only on the server.

Decisions that are open

How each measurement is judged
The first job in the build. It needs bike-fit knowledge, not programming. This is where your input matters most.
Which AI service reads the PDFs
Claude or OpenAI. We'll try both on the real KTM and Van Rysel pages and keep the one that reads the tables best.
Other seven measurements
Stored when available, not shown yet. Showing them later is a display change only.

Words you may hear

PWA
A website that can be installed on a phone like an app.
Adapter
The small per-brand module that reads that brand's PDF.
Container / Docker
A sealed box that holds the app so it runs the same everywhere.
CI
Automatic checks that run on GitHub each time code changes.
